`clearAllRateLimits()` (`server/rateLimit.ts`) only clears the in-memory rate-limit `Map`s of the process that imports it. In the Pre-Publish Gate's Stage 2c ("HTTP integration tests"), the live server is started via `npm run dev &` in one workflow step and the vitest test files run as a separate `npx vitest run ...` process in the next step — two different Node processes. A test file's `beforeAll`/`beforeEach` call to `clearAllRateLimits()` clears only its own disconnected copy of the module; the server actually handling the HTTP requests never sees it cleared. This has always been true of every limiter in that file — it only started causing failures once a route got its first real rate-limit enforcement, because before that nothing there consulted the limiter at all.

Confirmed twice now, same day (2026-08-26): SST-1474 (`SIGNUP_MAX_ATTEMPTS` 10→50, commit f6a3d75a) and this session's SST-1475 forgot-password fix (`PASSWORD_FORGOT_IP_MAX_ATTEMPTS` 10→20, commit 5cb30249, landed on `2026-v1`). Both times the actual failure mode was: Stage 2c's ~8 HTTP integration test files run sequentially (`fileParallelism: false`, `sequence.concurrent: false` in `vitest.integration.config.ts`) against ONE live server, so every call to a given route from every file shares one IP-keyed rate-limit bucket regardless of file boundaries — and any test file reusing one shared email/user across many calls to an email-keyed route shares one email bucket too, with `clearAllRateLimits()` doing nothing to reset it between tests.

**Why:** No test-only HTTP endpoint exists to reset the live server's rate limiter (checked during SST-1475 investigation — grepped for `clear-rate-limit`, `test-only`, etc., found nothing). `clearAllRateLimits()` is only ever imported directly by test files, never exposed over HTTP, so it can never reach a rate limiter running in a different process. Given the choice between building that endpoint and adjusting ceilings/test volume, the founder-approved precedent both times was the latter — see [[feedback_verify_a_reviewers_evidence_not_their_judgement]]-style rigor: compute actual Stage 2c call volume per route (grep the exact test files in `.github/workflows/pre-publish.yml`'s Stage 2c list) before picking a new ceiling, rather than guessing.

**How to apply:** Before adding real enforcement to ANY previously-unenforced rate limiter reachable from Stage 2c's routes, or before trusting a `clearAllRateLimits()` call in an HTTP integration test to actually isolate that test's rate-limit state, compute total legitimate call volume for that route across every Stage 2c file (not just the one being edited) and confirm the ceiling has headroom above it — both per-IP (shared across ALL Stage 2c files) and per-any-other-key like email (shared within whichever single file reuses that key). If a route's rate-limit key has a genuine security rationale for staying tight (e.g. an anti-harassment email cap, not just a generic volume cap), prefer restructuring the test file's own call pattern (fresh user/email per test, or minting DB fixtures directly instead of routing through the limited endpoint) over raising that specific ceiling — see this session's `tests/password-reset.integration.test.ts` and `tests/email-service.integration.test.ts` fixes for the pattern.
