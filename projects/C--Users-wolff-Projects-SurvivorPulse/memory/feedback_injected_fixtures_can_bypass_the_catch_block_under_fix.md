**Injectable-fixture tests can bypass the exact code being fixed if the fixture replaces the OUTPUT of a failure path instead of exercising its INPUT.** Found 2026-09-02 building SST-1516 (`server/scheduleHealthcheck.ts`): the historical bug was `checkTableForNulls` catching its own query error and returning `nullCount: 0`. First draft of the fix kept a try/catch *inside* the DB-querying function, converting a caught error into `{status: 'error', error: msg}` there. Every test injected a fake `probe` that returned pre-built `TableNullCheck[]` fixtures directly (including ones with `status: 'error'` already set) — so all 20+ "inconclusive" tests passed while the real catch-and-convert block sat completely unexercised. Confirmed with a mutation: reverting that catch block back to `return {status:'ok', nullCount:0}` (the literal original bug) left the suite green, invariant-check proved the mutation actually applied.

**Fix:** move the catch-and-convert logic OUT of the injected dependency and INTO the orchestrator that the DI seam wraps — i.e. the prober just *throws*, and the loop calling it does the `try { push ok } catch { push error }`. Now the same fixture-injection mechanism (a fake `probe` that throws) drives the exact code path that used to hide the bug. Same root cause as [[feedback_guard_the_wire_not_just_the_helper]] (a mutation reaches code no test's call graph touches) but the shape is different enough to name separately: that memory is about a call site stopping short of invoking a helper; this is about a fixture masquerading as the helper's *output* and skipping the helper's *failure-handling logic* entirely. Rule of thumb: if a dependency you're injecting for testability has a try/catch inside it, ask whether the catch itself is now untestable — usually the catch belongs one level up, in the code that calls the (now-simpler, throwing) dependency.

**A fix's own tests structurally cannot catch a design-intent regression the author didn't know they were making.** Same ticket: the original code's production path logged `JSON.stringify({type: 'SCHEDULE_TYPE_NULL_ALERT', ...})`, commented "structured error log that can trigger alerts" — real intent for future log-based alerting, though nothing in the repo currently consumes it (verified by grep — no Datadog/Sentry/PagerDuty/CloudWatch config anywhere). The fix replaced it with a human-readable string. Every test the author (me) wrote passed, because none of them asserted the OLD shape had to survive — that assertion never occurred to me, since I was focused on the bug I knew I was fixing. A dispatched code-review persona (Felix, in this repo's multi-persona triage) caught it on a second, independent read of the diff. **Why to apply:** a green suite after a fix proves the NEW requirement holds; it says nothing about incidental OLD behavior that wasn't written down anywhere as a requirement. Independent review — a second pass over the actual diff, not the fix-author's account of what changed — is the only thing structurally positioned to catch this, because only it looks at what changed rather than only at what was supposed to change. Don't skip the review step even when a fix is "obviously correct" and fully unit-tested.

Building first (per the explicit order) then running the retroactive triage against the *actual landed fix* worked fine here and arguably gave the triage panel better material (Vlad could verify a real diff instead of reviewing a proposal) — but the skill should be checked *before* filing a Bug-typed ticket in the first place, not only remembered later when about to move it through Kanban.
