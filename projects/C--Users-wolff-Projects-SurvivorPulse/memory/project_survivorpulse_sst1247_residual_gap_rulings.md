SST-1247 fixed Home's "Add your first pool" empty state wrongly showing for users with a real pool in a non-current season. Code review surfaced two related, NOT-fixed residual gaps (documented in `tests/currentSeasonDebriefHasPoolsInOtherSeasons.sst1247.test.ts` TC-3/4/6 and `server/services/currentSeasonDebriefService.ts`'s off-season branch). Brought to the founder for a product call; both are now resolved:

1. **Off-season copy — ruling: leave as-is, no change.** During off-season, `resolveHomeState` always resolves `"new-user"`, and the existing `HOME_PRIMARY_ACTION_RETURNING_USER_COPY` ("No pools yet this season... get started this season") fires unmodified whenever `hasPoolsInOtherSeasons` is true — including for a user whose only pool was in the season that JUST ended. Verified via `currentSeasonDebriefHasPoolsInOtherSeasons.sst1247.test.ts` TC-3 that `seasonInfo.season` during off-season already refers to the UPCOMING season, so this copy path is reached correctly, it's just not off-season-specific. Founder judged this cosmetic (copy isn't false, just occasionally early) and not worth a distinct variant.
   **Why:** low severity — nothing shown is inaccurate, only potentially premature deep in the off-season.
   **How to apply:** don't re-raise this as a gap; if UI copy work touches `client/src/components/home/homePrimaryActionCopy.ts` again, no off-season branch is expected or missing.

2. **Zero-entry current-season pool — ruling: approved for build, both halves. ✅ RESOLVED — both halves shipped, confirmed 2026-08-24.** `PoolCreationWizard.tsx`'s entry-creation step (~line 425-427) failed non-fatally and silently ("logged, not surfaced as modal"), which could leave a real current-season pool with zero entries. Confirmed reachable and covered by TC-6. Because `hasPoolsInOtherSeasons` is correctly `false` for these users (no OTHER-season pools), they saw the plain "Add your first pool" copy despite already having a pool — this one read as actively wrong, not just imprecise. Founder chose **"fix root cause + add copy"**, routed to Pam (scope) → Ann (requirements) 2026-08-03:
   - **Root cause — [SST-1257](https://app.notion.com/3b129ce5833d817fa6dec5ee9a5a339b) "Pool entry-creation failures: durable logging, safe recovery, no silent duplication" — Status: Done, completed 2026-08-04.** Durable server-side logging on failure, bounded inline retry, a per-pool recovery surface, reconciliation against actual entries (no duplicates), a read-only diagnostic script, and identical treatment for pools broken before the fix. Confirmed live in code 2026-08-24: `PoolCreationWizard.tsx`'s entry-creation `catch` block now reads "SST-1257 (A-1/A-2): a bounded inline retry self-heals transient per-entry failures... durably logged server-side — never silently swallowed as the old comment here used to claim." The remaining `catch {}` is documented defense-in-depth only, not the original bug. SST-1257 also folded in a related finding (Game Plan's `CockpitEmptyState` showing generic "no pool" copy for this exact same zero-entry case) rather than deferring it.
   - **Copy — [SST-1258](https://app.notion.com/3b129ce5833d815cb59fd7b31a5a126c) "Home: a third state for a real pool with no entries yet" — Status: Done.** The distinct Home copy variant.
   - SST-1257's own Notes field confirms the link back to this exact ruling verbatim: *"Founder approved 'fix root cause + add copy' 2026-08-02/03."*
   **Why:** a copy-only fix would have left the underlying data-integrity bug (silently empty pools) able to recur indefinitely — this is why both tickets, not one, were required to close this out.
   **How to apply:** don't re-raise this as an open gap or re-route it through grooming again — it's done. If a zero-entry current-season pool is ever seen again, that's a regression against SST-1257/SST-1258, not a rediscovery of this ruling.
