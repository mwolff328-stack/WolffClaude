Found twice in SST-1757 (duplicating-picks research pages), each time by a closing/re-verification pass, never by the slice's own unit tests.

**1. A fixed SVG `viewBox` scaled down via CSS `width` renders illegible axis text, invisible to jsdom.** `SurvivalLineChart.tsx` shipped with `viewBox="0 0 800 380"` and Tailwind `text-[10px]`/`text-[11px]` classes inside the SVG coordinate space, with `className="w-full"` doing the actual sizing. jsdom's `getComputedStyle` reports "10px" whether or not the SVG is actually being scaled down by the browser — it has no layout engine, so it can't see that at 375px width the 800-unit viewBox scales by ~0.47x and the "10px" text renders at ~4.7px on screen. Every jsdom test for this component passed clean through three slices (S5 built it, S10's closing pass didn't catch it either) because none of them measured a real rendered pixel dimension.

**2. The browser's native disabled-attribute focus fixup beats a React `useEffect`, invisible to jsdom.** `ViewBasisPicker.tsx`'s fix for a picker option becoming disabled while it holds focus read `document.activeElement === realisticButton` inside a `useEffect` to decide whether to move focus to the new effective option. In a real browser, setting the `disabled` attribute on the currently-focused element can synchronously fire the native focus-fixup (blur/focusout to `<body>`) *before* React's effect runs, so `activeElement` is already `<body>` by the time the effect checks it — the focus-move silently no-ops and a keyboard user is stranded. jsdom does not simulate native disabling-fixup behavior at all, so a jsdom test asserting `document.activeElement` after triggering the state change proves nothing: it can only observe the state jsdom itself produced, which never included the race. The fix (track focus via a `focusin`/`focusout`-driven ref, not a reactive `activeElement` read) was found and RED-proofed only by a Playwright run built specifically to reproduce the browser's native ordering, triggered via a real `HTMLElement.click()` on the DOM (a *pointer* click actually happens to sidestep the race, since pointer-down focus-follow runs before the click's `onChange`, so the reviewer had to specifically use a native `.click()` call to expose the hazard — a naive "click it with Playwright" test would have missed it too).

**Why both slipped through multiple slices and one closing-verification pass:** a jsdom test can be a perfectly good RED-proof of its own logic (mutate the code, watch the assertion fail, restore, watch it pass) while being structurally blind to the actual browser behavior the AC cares about, because jsdom has no real layout/rendering engine and doesn't implement every native DOM-mutation side effect (like disabled-attribute focus fixup). This is a different failure mode than [[feedback_jsdom_normalises_inline_styles_two_traps]]'s style-serialization traps — those make a real jsdom-observable value wrong or vacuous; this is jsdom having no observable signal for the defect at all, in either direction.

**How to apply:** any AC naming a pixel size, a CSS breakpoint, a "real-pixel" or "no scaling" requirement, or a focus-management guarantee around a DOM-mutation side effect (disabled/hidden/removed while focused) needs a **Playwright** (or equivalent real-browser) proof, not a jsdom one — and that proof must measure the actual failure mode, not trust `getComputedStyle` or a simulated state transition:
- For pixel/scaling claims: measure `element.getBoundingClientRect()` and the actual `viewBox`→rendered-pixel ratio, and include a negative control that plants the old broken shape (a wider fixed viewBox CSS-scaled down) to prove the measurement would actually catch it.
- For focus-management-around-disabling claims: trigger the state change via a real DOM event (not React state injected directly) while focus is genuinely on the element via `.focus()`, and check `document.activeElement` only after that real event has settled — and test more than one triggering mechanism (a pointer click may not reproduce the race that a programmatic `.click()` or a keyboard-driven change does).

See [[feedback_jsdom_normalises_inline_styles_two_traps]] for the related but distinct family of jsdom serialization traps, and [[reference_survivorpulse_lessons_index]] for the fuller lessons index.
