SurvivorPulse tests/ uses `vi.mock(specifier, factory)` extensively. Vitest hoists every top-level `vi.mock()` call above ALL of a test file's own module-scope `const`/`let` declarations (and above its own imports). If the factory — or a nested closure it returns — dereferences such a binding before its declaration statement has executed, referencing it throws `ReferenceError: Cannot access 'X' before initialization`. This took down Pre-Publish Gate Stage 2a on 2026-09-08 (`tests/poolEntriesCurrentWeekPick.integration.test.ts`, `TEST_SEASON`).

**Mechanism, empirically verified (SST-1600), not assumed:** nesting depth inside the factory does NOT predict risk. The confirmed bug was nested two levels deep (`vi.mock(async () => {... getCurrentNFLSeason: vi.fn(() => TEST_SEASON) ...})`) and a directly-analogous "declare mock object, reference it in the returned object" pattern used in ~200 other files does NOT throw in practice. The real trigger: whether something in the test file's *synchronous import chain* (an eagerly-evaluated top-level call in some OTHER module the file imports, directly or transitively) calls into the mocked function before this file's own const/let executes. Repro built and verified: a **static** import (not dynamic `import()` from inside an `it()` — that runs too late) of a module that calls the mocked function at its own top level reliably reproduces the ReferenceError; wrapping the referenced value in `vi.hoisted()` fixes it.

**Fix pattern**, matching the repo's own established convention (116 files already used it before this story): `const X = INIT;` → `const X = vi.hoisted(() => (INIT));`, or for multiple interdependent values in one file, `const { A, B } = vi.hoisted(() => { ...; return { A, B }; });`. For a mutable `let` that gets reassigned later in the file (e.g. `let mockLocation` toggled per-test), the SAME simple wrap works and preserves reassignability: `let mockLocation = vi.hoisted(() => "/pools");` — confirmed empirically; do NOT over-engineer this into the `state.mockLocation` mutable-object pattern unless the value has no meaningful default.

**Sweep tooling gotcha — typescript@7 in this repo (package.json `"typescript": "^7.0.2"`) is the native/Go-ported compiler and no longer ships the classic JS compiler API** (`ts.createSourceFile`, `ts.ScriptTarget`, etc. are all `undefined` when imported — `node_modules/typescript/lib/` only has `getExePath.js`/`tsc.js`/`version.cjs`, no `typescript.js`). `ts-morph` and any AST tool built on the classic API will not work here. Use `@babel/parser` + `@babel/traverse` (both already in `node_modules` as transitive deps) with the `typescript` plugin instead.

**Babel gotchas hit while building the sweep** (both real, both would silently produce wrong results if not handled):
1. `path.isReferencedIdentifier()` does **not** filter out identifiers that appear only in TS type position — `(p: EmailSendParams) => {}` reports `EmailSendParams` as a referenced identifier. Must explicitly walk ancestors and exclude anything under a `TS*` type-space node (excluding the real-expression wrappers `TSAsExpression`/`TSSatisfiesExpression`/`TSNonNullExpression`/`TSInstantiationExpression`).
2. `path.traverse(visitor)` only visits **descendants**, never the root path itself. A bare-identifier initializer (`const X = Y;`, no wrapping expression — `Y` IS the entire init, with no children) is invisible to a naive `initPath.traverse({Identifier...})` scope-aware walk. This exact gap let a mechanical codemod wrap `let queryResult: unknown = QUERY_RESULT;` into `vi.hoisted(() => (QUERY_RESULT))` — still broken, since `QUERY_RESULT` itself wasn't hoisted — and it slipped through until the full-suite verification run caught the collection-time failure. Must special-case: if `initPath.isIdentifier()`, check it directly in addition to traversing its (nonexistent) descendants.

**Deferred, not swept-and-fixed** (SST-1600): 36 `let X: Type;` declarations with **no initializer at all** (assigned later in `beforeEach`), referenced only inside `vi.fn(async (...) => {...})` route/service-handler mocks needing live runtime args (userId/week/season) — genuinely low reachability (unlike a nullary "what season is it"-shaped accessor, nothing plausibly calls these eagerly at import time), and no cheap mechanical fix exists (would need either `undefined as unknown as T` casts repeated 36x or a larger refactor to a shared mutable-object property). Also 2 declarations whose initializer calls an *imported* function (`buildFixtureTag`) — `vi.hoisted()` callbacks run before imports, so this needs real restructuring, not a wrap. Full file/declaration list is in the SST-1600 Notion ticket's Notes field.
