Facts about the entry-recommendations payload + its client cache, established building the SST-1018..1022 pick-modal batch (2026-07-24). The modal lives in `client/src/components/PickGrid.tsx` (`TeamPickerModal`); the row shape + transport are in `client/src/lib/entryRecommendations.ts`.

**Rank column (SST-1030, 2026-07-25, supersedes SST-1023):** the modal's Rank is ONE unified ranking over ALL displayed teams (available + used-when-toggled + selected) by `rankedSortKey` desc with a `teamId` tie-break → a UNIQUE rank per visible team (`overallRankByTeamId`); no-`sortKey` teams render "—" and sort last. Same map drives Ranked AND By Division. The list defaults to Rank ascending and the user's sort (col+dir) persists to localStorage `sp:pickModal:sort`. This REPLACED SST-1023's interpolation (available got 1..N, used/selected interpolated as count-above+1) which collided multiple teams onto the same rank — a PARTIAL ranking can't produce unique positions; rank the full displayed set in one pass. Consequence: turning "Show used teams" on renumbers available ranks (a used, non-selectable team can be Rank 1) — intended.

**`allTeams[]` is the RAW list and carries more than the client reads.** The server's `TeamRecommendation` (`server/services/optimizerService.ts`, ~line 157) already includes per-team **`spread: number|null`** (negated for the away line) — the client `EntryRecommendationTeam` interface just didn't declare it until SST-1019. `allTeams` "includes unavailable teams" (line 219 comment), each WITH full stats. So before assuming a new column needs backend work, check whether the field is already in the payload.

**`available` = eligibility, not kickoff-lock.** `available` is `isTeamEligibleForEntry(...)` (optimizerService ~line 1821). In a regular week `available:false` mostly means **already used by this entry** (still playing → still in `allTeams` with stats) or **bye** (no game → absent from `allTeams`). In playoffs it means **used** or **not-qualified** (not in payload); byes don't exist. A kickoff-started team is still `available:true` — the lock is enforced at SAVE time via a 409 `PICK_LOCKED`, NOT via the `available` flag. So "used" (from `/teams/usage`) and "unavailable" (the `available` flag) are DISTINCT facts; source used-ness from usage to show used teams with real stats while keeping bye/not-qualified hidden.

**Playoff weeks: the payload includes future-round teams as "BYE WEEK" entries (SST-1025).** For a single playoff week, `getWeeklyRecommendationsForEntry` builds rows from that week's games (so this-round teams have a real `opponentId`), then ALSO appends teams NOT playing this round that still carry future utility as bye entries: `opponentId: ''`, `matchup: 'BYE WEEK'`, `winProbability: 0`, `spread: null`, and `available: !used` (so they can be `available:true`). So "present in the payload / available:true" is NOT "playing this round" — the reliable round-scoping signal in the client is a **non-empty `opponentId`**. The pick modal filters playoff cells on that (Ranked, By Division, used rows, overall-rank pool, empty-state). Regular weeks: every team has a game (except real byes), so no filter is applied.

**Team usage (`getTeamUsageByEntry`) is already correct — scope it at the call site.** Passing `currentWeek` scopes "used" to `picks.week < currentWeek` (so the current/ future weeks' picks aren't counted). For a playoff pool + playoff week + season it also filters the exposed teams to those playing THAT week and removes eliminated teams (`getAlivePlayoffTeamIds`), and drops used teams not eligible this week. The `/teams/usage` route derives scheduleType from the POOL (playoffs_only → 'playoffs', else 'regular') — a regular_playoffs pool at a playoff week derives 'regular', so SST-1025 added an optional `scheduleType` query-param override. The pick modal now calls usage with `currentWeek + season + scheduleType` (the usage query key is `[...teamUsage(poolId,entryId), week, scheduleType]`; pick-save mutations still invalidate via the shorter prefix — partial match). Lesson: when a scoping bug appears, check whether the call site is under-parameterizing an already-correct function before touching the function.

**SST-1007 cache invariant, stated correctly:** the discriminator (`availableOnly` bool in `queryKeys.entries.optimizerRecommendations`) exists so the picker's SELECTABLE list (`availableOnly:true`, filtered) never caches a FILTERED subset under the same key the Season-Grid/Week-View cell reads (which needs the unfiltered `false` list, incl. the entry's own current pick). The invariant is "**don't cache a filtered subset under the shared unfiltered key**" — NOT "don't share keys." A second `useQuery` on the `false` key is SAFE (and dedupes) as long as its `queryFn` returns the unfiltered `allTeams` (SST-1021/1022 do exactly this to get used/selected teams' stats).
