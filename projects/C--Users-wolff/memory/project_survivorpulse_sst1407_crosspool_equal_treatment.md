# SST-1407: Cross-Pool Claims Equal Treatment (SST-1329 reversal)

Done 2026-08-19, shipped 2bd45edd/227ce913 on 2026-v1 (SST-1406's UI work landed on top afterward at ebeeffed, no conflict).

## What changed
Founder ruling 2026-08-19 (verbatim, given directly in chat): "Apply cross-pool distinctness to eliminated entries too. NOTE: this only applies to proposed picks, not actual picks." Follow-up: "I think we can treat all entries equally every time we apply a strategy... I don't think we want to give priority to live entries from a previous run."

This is a **deliberate reversal** of SST-1329 (8c914aac, "dead-but-simulated entries no longer consume cross-pool team claims") and its SST-1402/SST-1402-follow-on refinements (fb6b94e8, buyback-aware standing). `contributesToCrossPoolClaims` in `server/services/cockpitRecommendationService.ts` is now unconditionally `true` for every past-season EntryContext row -- alive/eliminated/buyback status no longer matters for cross-pool claims participation. Fixed the live-confirmed bug: CMEA Prototype Demo Pool and Goldflam Suicide 2025 (2025 season, nearly all entries eliminated) produced 4 exactly-identical entry pairs because the old gate left `crossPoolClaims` near-empty.

`crossPoolClaimsEliminationWeek` (SST-1385, an independent week-level cap keyed off each entry's OWN persisted Proposed-track pick history) is untouched and still governs whether a week's claim gets WRITTEN, separate from the always-true participation gate.

## Reusable fact: an entry's REAL Proposed-track elimination week is NOT the same as its Actual-track `eliminationWeek` column
Two independent axes, both legitimate and both already documented elsewhere in the codebase (SST-1385's own doc comment uses this exact shape as its canonical example): an entry can be genuinely alive on Actual (`isAlive:true`, `eliminationWeek:null`) while its own separately-persisted `proposed_picks` history independently shows a real recorded loss -- computed by walking that entry's own `GET /api/pools/:id/proposed-picks` results in week order, applying the pool's real buyback rule (`allowBuybacks`, `revivalsPerEntry`, `entryRevivalDeadline`, `strikeCount` -- a loss at/before the deadline with a revival available doesn't count, the loss consumes it and the walk continues; the next loss, or a first loss after the deadline, is the real cap). This tripped up a live-verify review twice in one session (see Process learning below) before being reconciled with real data both times.

## Process learning (governance pattern worth repeating)
A live-verify comment that reports a residual anomaly (here: 41 cross-pool team overlaps in weeks 5-18, out of an otherwise-clean fix) and explains it away in prose without deriving the explanation from real records is **not evidence** -- it's a second unverified claim stacked on the first. Vlad (QA persona) correctly returned CONDITIONAL twice on exactly this pattern: once on the headline "these overlaps are expected" assertion, and again on a specific number inside the reconciliation itself (an entry's computed elimination-cap appeared to contradict an earlier "alive" description). Both times the fix was identical: pull the actual persisted records the mechanism reads from (proposed_picks results + pool buyback settings, via the live API) and recompute the claim by hand, rather than restate it more confidently. Don't accept "expected/harmless" from an agent (including yourself) without a data-derived proof of *why* -- especially when the anomaly count is nonzero and the underlying claim (bug fully fixed) is the thing being sold.
