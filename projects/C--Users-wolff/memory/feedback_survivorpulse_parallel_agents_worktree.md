When running multiple code-editing agents (e.g., Felix implementation sessions) for SurvivorPulse, give each its own git worktree (Agent `isolation: "worktree"`) or run them sequentially. Do NOT let two implementation sessions share the same worktree.

**Why:** During SST-563 (2026-06-21), a concurrent SST-563 session shared the worktree. An out-of-scope change (removing the "My Entries" sidebar panel) got "swept into" the wrong commit (44ec349e), commit attribution became confusing, and a separate test-cleanup commit (e6a0606a) appeared that no single agent fully accounted for. It took manual git forensics to reconstruct the true unpushed chain before pushing.

**How to apply:**
- Parallelize build agents only with worktree isolation; otherwise sequence them.
- When code-reviewing, review the actual branch HEAD (and the full unpushed range `origin/<branch>..HEAD`), not just one named commit — concurrent commits can land that a single-commit review never sees.
- Before pushing, always run `git log origin/<branch>..HEAD` and verify every unpushed commit is accounted for; run the relevant tests locally yourself rather than trusting agent self-reports.

**Auto-push hook + concurrent session — don't panic, don't force-push (2026-06-24):** SurvivorPulse has an autonomous-operation behavior that AUTO-PUSHES `2026-v1` right after a commit. During the SST-568-B/D parallel build, immediately after my integration commit `f02b9fc8` a hook pushed it; a concurrent founder session (Michael, "My Strategy" wizard) then pulled it and stacked 6 more UI commits ON TOP, and my local branch fast-forwarded to their tip. Symptoms that look alarming but are BENIGN: `git push` says "Everything up-to-date"; `git log -6` no longer shows your commits; HEAD is on someone else's commits; working tree looks like yours reverted. **Correct diagnosis (never trust "up-to-date"):** `git merge-base <yourcommit> HEAD` == `<yourcommit>` proves your work is an ANCESTOR of the current tip (i.e. safely in history, just buried under newer commits); `git ls-remote origin refs/heads/2026-v1` shows the true remote tip; `git cat-file -t`/`git ls-files`/grep confirm your artifacts are present; re-run your suites on the current tip. Only if merge-base does NOT equal your commit is anything actually lost — and even then recover via merge/cherry-pick of the still-present objects, **NEVER** via `git reset --hard` or `git push --force` (that would clobber the concurrent session's work). Re-verify tests on the combined tip, since another session's commits now sit on top of yours.

**Explicit-path staging is NOT sufficient protection — `git commit -- <pathspec>` bypasses the index (2026-07-17):** During the SST-890/901/902 triple-parallel build (same worktree, all under strict "stage only your files" instructions), the sweep happened anyway: `git commit -- <path>` commits the CURRENT WORKING-TREE content of the named paths, not what was staged, so one agent's commit captured another agent's in-flight edits to shared files (SeasonGridSection/WeekViewSection), and its later `--amend` back to "only my diff" silently REVERTED a third agent's already-pushed change (SST-901's prop threading vanished from origin) while leaving SST-890's integration stranded uncommitted in the working tree. Detection: grep origin blobs for each story's distinctive markers (`git show origin/<branch>:<file> | grep <marker>`) plus `git status` for stranded modifications — agent self-reports conflicted and were BOTH partially wrong. Fix: verify the stranded diff carries the missing work, re-run tsc + the affected component suites yourself, land it as an explicit reconciliation commit (be5b8e28). Rule: agents editing DIFFERENT files in one worktree is tolerable; two agents editing the SAME file is not parallelizable at all — serialize any stories whose file sets overlap, even by one file, and audit origin markers per story after any concurrent batch.

**DELETIONS ARE THE WORST CASE — `git rm` puts your work in the SHARED INDEX where another agent's broad `git add` will steal it, and pushing a half-swept deletion leaves origin RED (2026-07-22):** During the Pool Command Center removal (4 files, 1027 lines), a concurrent session committed AND PUSHED `ee0fb6d8 feat(auth): …` whose broad `git add` swept all four staged deletions into that unrelated auth commit. Because it was already on the remote, history rewrite was off the table. The result was a genuinely broken `origin/2026-v1`: the files were gone, but `client/src/lib/__tests__/sortableListKeyboardSensor.test.ts` still `readFileSync`'d `AllocationGrid.tsx` (ENOENT) and two `myPicks` tests still `vi.mock`'d a module that no longer resolved. Replit syncs from origin, so the dev app tracks a red tree until repaired. Verify the breakage from the REMOTE, not the local tree: `git show origin/<branch>:<test file> | grep <deleted name>` plus `git cat-file -e origin/<branch>:<deleted file>` (fails ⇒ deleted there) proves it objectively.
**RULE: in a shared checkout, delete files with plain `rm`, never `git rm`.** `rm` leaves the deletion as an unstaged working-tree change that only your own explicit `git commit -- <paths>` picks up; `git rm` stages it immediately into the index every other agent shares. This is the deletion-specific counterpart to the 2026-07-17 finding above — explicit-path staging protects nothing once the change is already in the index.
**Deletion checklist that caught real latent breakage this round:** grep the deleted symbols across `client/ server/ shared/ tests/ e2e/ scripts/` for STRING literals too, not just imports — `readFileSync`/`vi.mock`/route constants reference files without importing them. Two live landmines were found this way: a tripwire allowlist doing `readFileSync` on the deleted path, and a `describe.skip` block in `tests/myStrategy.sst562.test.tsx` that `readFileSync`'d the deleted page and would have exploded the moment anyone un-skipped it. Also run `npm run build`, not just `tsc` — for a UI deletion Vite catches unresolved imports that tsc tolerates.
**Type-only imports defeat component greps.** I called `my-picks.tsx`'s `TargetsZone` import dead because `<TargetsZone` had no renderer. It was `import type { TeamTarget } from ".../TargetsZone"` — a live TYPE import used at 4 sites. A component with no renderer does NOT mean its module is orphaned; grep the module path, not the component tag.

**WHAT ACTUALLY WORKED (2026-07-23, SE-91 batch of 5 stories, zero contamination):** run BUILDERS in the shared checkout only when their file sets are disjoint (Deb on `client/`, Felix on `server/` — fine), and run every MUTATION-BUILDING REVIEWER in `isolation: "worktree"`. Reviewers are the under-appreciated hazard: our review standard requires building and RUNNING mutants, so a reviewer WRITES to the tree exactly like a builder does. A reviewer of a server story and a builder of another server story both editing `server/routes.ts` is the same unparallelizable overlap as two builders. Worktree isolation makes it a non-issue. Tax: `npm install` per worktree (node_modules is not shared) — acceptable for an overnight run, and cheaper than one contaminated commit.
- Deb's own defense when she found another session's uncommitted work in a file she needed: build a patch of ONLY her hunks and `git apply --cached` it, instead of `git add`. That is the correct third option alongside plain-`rm`-not-`git-rm` for deletions.

**THE AUTO-PUSH HOOK MAKES YOUR PUSH CARRY OTHER AGENTS' COMMITS — verify what you are actually publishing (2026-07-23):** `git push` publishes the whole branch, not your commit. When I pushed SST-959's fix, the range `f6451023..39c4e78a` silently carried up Deb's two SST-960 commits that were sitting underneath — **while that agent was still running.** No harm this time (both were complete commits), but had her second commit been a half-finished intermediate state, I would have published a broken tree to origin, which Replit syncs from → red dev app. Before pushing in a shared checkout, run `git log --oneline origin/<branch>..HEAD` and account for EVERY commit in the range, not just your own; if a commit belongs to a still-running agent, either wait for it to report or confirm it is a complete unit. "Everything up-to-date" on your own push often means the hook already pushed it for you — cross-check with `git log --oneline -6 origin/<branch>` rather than trusting the message.
