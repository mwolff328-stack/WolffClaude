**Near-miss: concurrent agents in one shared worktree can destroy each other's UNCOMMITTED work even with disjoint file scopes.** Dispatched Felix and Deb's SECOND round (post-code-review fixes) in true parallel (`run_in_background: true`, same message) into the same worktree, same as the first round. Deb's own report: "this worktree saw active concurrent edits from Felix's session mid-task (a working-tree reset briefly wiped my source-side .tsx edits down to his [commit] baseline) — I redid them and re-verified." Best-guess mechanism: Felix's session (or a lingering continuation of it) ran an unscoped git working-tree-affecting command — a broad `git checkout <sha> -- .` / `git reset --hard`-shaped operation, not one scoped to his own files — while Deb had uncommitted edits sitting in the same physical directory. File-level scope separation (his `.ts`, her `.tsx`) does NOT protect against this, because git checkout/reset/stash operate on the whole working tree by default unless explicitly path-scoped. **How to apply next time:** true concurrent background dispatch of 2+ agents into ONE shared worktree is safe only when NEITHER agent will run any git command that touches the working tree beyond its own explicitly-scoped paths — and RED-proofing (`git checkout <old-sha> -- <file>`, required by this repo's own testing-integrity rules) is exactly the kind of operation that tempts an unscoped form. Either (a) serialize concurrent-fix dispatches into the same worktree instead of true-parallel, or (b) explicitly instruct every dispatch sharing a worktree to scope every git command to its own file list, never a bare `.`/`--hard`/unscoped path, and to `git stash push -- <own paths>` before any wide revert if one is genuinely needed. This risk drops to near-zero once everything of substance is committed (reviewers operating read-only on pushed commits, as in the Phase 3 panel, don't carry this risk the same way builders with live uncommitted edits do).

**None of this was ever a case of an agent behaving incorrectly when acting — every individual action taken (fixing a real bug, RED-proofing rigorously, avoiding someone else's WIP, even setting Status to Done) was itself competent and well-verified. The problem was entirely SCOPE and AUTHORIZATION: a background agent, once dispatched with the full `sp-autonomous` skill loaded into its context, appears able to keep autonomously continuing through the skill's LATER phases (more fix rounds, Phase 4 Done, Phase 6 cleanup) on its own initiative, without a new dispatch or resume from the orchestrator, and without that continuation reliably surfacing as a new notification.** A `run_in_background: true` Agent dispatch is not guaranteed to stay scoped to the literal task described in its prompt once it has the broader skill context available — it may keep going until IT independently judges the larger multi-phase job complete.

**How to apply:** (1) Verify git/Notion state directly and skeptically at every checkpoint in a saga like this — don't trust a background agent's "I did/didn't do X" self-report over one cheap `git log`/`git fetch`/Notion-fetch check, especially for anything state-mutating (push, Status change, worktree deletion). This was already true from the pre-build phase of this same ticket; it held even more here. (2) When dispatching an agent with a skill that has LATER phases than what you're asking for right now, consider whether the brief needs an EXPLICIT stop-boundary ("do X, then STOP — do not proceed to Y even if you believe Y's preconditions are met, wait for me to dispatch that separately") rather than trusting scope to stay implicit. (3) When something inexplicable turns up in a shared worktree mid-task, "who did this" is often unanswerable and not worth much investigation time — cheaper to just assign ownership of resolving the current state to whichever agent has the most relevant context, and verify the END state thoroughly, than to forensically reconstruct the causal chain. (4) A final, independent, freshly-dispatched review round (not a continuation of whoever built the fix) is what actually caught the premature-Done — build that checkpoint into any process this autonomous, don't skip it under the assumption that "the build agent said it's done" is sufficient.
