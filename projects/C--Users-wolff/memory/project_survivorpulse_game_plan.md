## Apply-write-failure bug (SST-916) RESOLVED 2026-07-20 — engine used-teams tracking
Founder hit "1 pick could not be set" applying an archetype to all entries with Spread + Replace-confirmed ON (6 written, 1 failed; generic SST-909 msg, raw error server-side). Root cause (Felix, commit 67bf27d5): resolveUsedTeamsAsOfWeek in cockpitRecommendationService.ts (the SST-881 self-poisoning fix) freed EVERY week >= currentWeek from the entry's usedTeams set, ASSUMING the engine recomputes the whole [currentWeek..endWeek] horizon each run. WRONG early-season: only currentWeek (±1) has real odds (basis:'odds'); later weeks are basis:'projected' → gameplanApplyService turns them into 'skipped-projected' no-writes. So an entry with a REAL persisted pick in an untouched future week (manual pick-ahead or leftover) had that team's usage invisible to the engine → engine re-recommended it for currentWeek → under overwriteConfirmed it got WRITTEN → storage.replaceEntryPeriodPicks' SEASON team-use-limit check (storage.ts ~3670, "Team X already used in another period this season") correctly rejected it. Correlates exactly with Replace-confirmed ON (without it the confirmed cell is never rewritten so the collision never surfaces). FIX: a week is freely-re-decidable only when >= currentWeek AND actually in usableWeeks (this run's real fwdInput.weekData coverage); the constraint moves EARLIER (engine never proposes a team the write layer would reject) — NO invariant weakened, storage SEASON check byte-identical. RED-first regression test tests/gameplanApplyFutureUsedTeamCollision.integration.test.ts (DB-asserted: wk1 written, future wk untouched, no shared team). Vlad PASS-WITH-NOTES; SST-881 test still green (it seeds all 18 weeks so currentWeek always in usableWeeks). LIVE-verified: apply returns 200 (was 207), 0 failed. RESIDUAL fast-follow SST-917 (LOW, fails-safe): later-season, if a freed future week's own recompute resolves tied/null AFTER the engine claimed that team for currentWeek in the same pass, the same symptom could resurface in a rarer shape — write-time check still protects integrity, untested. Also detail-list UX (Deb, c50ccd15): apply auto-fill rows now show "PoolName — EntryName · Week N" (was raw entry UUIDs), client-side map from the entries prop, UUID fallback.
🎓 LESSON: a "free the team for re-pick" optimization must be gated on the data the engine ACTUALLY recomputes this run, not on a horizon it's ASSUMED to recompute — early-season odds coverage is partial, so "week >= currentWeek" ≠ "week the engine will rewrite." A write-time data-integrity check (team-use-limit) is the safety net that turned a silent bad-write into a visible failure; keep those checks strict and fix the proposer, never loosen the check.
