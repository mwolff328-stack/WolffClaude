Bug report (founder, 2026-07-21): My Pools card for "2026 Regular Season Test Pool 1" showed 2 entries (Entry 1/Entry 2) while Pool Details showed 1 (Test Entry 2); and a Regular Season + Playoffs pool was labeled just "Regular Season". Two independent root causes, fixed in commits b8fbc76d + ed49ea7c.

**Gotcha 1 — entry roster cache-key split.** My Pools / Portfolio read the USER-scoped roster `["/api/user/entries"]`; pool-detail surfaces read the POOL-scoped `["/api/pools", poolId, "entries"]`. Global queryClient sets `staleTime: Infinity` + `refetchOnWindowFocus:false`, so `/api/user/entries` NEVER self-refetches — it updates ONLY on explicit invalidation. Any entry add/rename/delete surface that invalidates only the pool-scoped key leaves My Pools persistently stale (different counts AND names) until a full reload. `MyPoolsCard`/`pools.tsx` already invalidate `/api/user/entries` correctly; `PickGrid` (the detail page's roster grid) did not — fixed. Safety net: `pools.tsx` `/api/user/entries` query now uses `staleTime:0 + refetchOnMount:"always"`. NOTE: `queryKeys.entries.user()` returns `['/api/user-entries']` (hyphen) which does NOT match the real slash key — a broken/unused trap; invalidate the literal `["/api/user/entries"]`.
NOW FIXED across ALL surfaces (commit 573b6f42, 2026-07-21): the four remaining gapped surfaces — `EntriesTab.tsx` (add/rename/delete/revive), `pool/EntrySettingsSection.tsx` (rename/buyback/delete), `pool-settings/PoolSettingsTab.tsx` (save-settings entry edits), `pages/pool-detail.tsx` (add/delete) — now each invalidate the literal `["/api/user/entries"]` alongside the pool-scoped key. Regression tripwire added on PoolSettingsTab save handler (spies QueryClient.invalidateQueries, asserts the slash key), proven RED→GREEN. tsc clean; entrySettingsSection + PoolSettingsTab suites green (54 tests).

**Gotcha 2 — legacy poolType collapses regular_playoffs.** `pools.poolType` (legacy) only holds 'regular_season'|'playoffs'; the canonical `pools.poolScheduleType` holds 'regular'|'regular_playoffs'|'playoffs_only'. `poolScheduleTypeToLegacyPoolType('regular_playoffs')` → 'regular_season'. Any UI labeling schedule from `poolType` mislabels a regular_playoffs pool as "Regular Season". Use `poolScheduleType` + `POOL_SCHEDULE_TYPE_LABELS` (shared/scheduleType.ts). Same trap could affect `isPlayoffs(pool.poolType)` history-flag logic in MyPoolsCard (not fixed — regular_playoffs treated as non-playoff there).

**Gotcha 3 — name vs nickname divergence on rename (fixed 301a3a4a, 2026-07-21).** Entries have BOTH `name` (NOT NULL) and `nickname` (nullable), set to the SAME value at creation (POST: `nickname: req.body.nickname || name`). Most surfaces display `nickname || name` (nickname-first) — MyPoolsCard/pools.tsx/EntriesTab/PortfolioSnapshot; pool-detail/pool-dashboard show `nickname` ONLY. But `PickGrid` (the pool-detail roster grid) displays/edits/writes `name` ONLY. So renaming on the detail page set name="Blue" while nickname stayed "Entry 2", and My Pools kept showing "Entry 2" (NOT a cache miss — count synced, name didn't). Fix: pure shared helper `shared/entryNameFields.ts` `syncEntryNameFields()` used in PATCH /api/pools/:poolId/entries/:entryId mirrors a single-field rename onto BOTH columns (respects both when both explicitly sent; blank/absent never clobbers → buyback-only PATCH safe). Single-point server fix covering ALL rename surfaces (PickGrid/MyPoolsCard send name, EntriesTab sends nickname). NOTE: pre-existing diverged entries need ONE more rename to reconcile; the fix only guarantees future renames stay in sync.
