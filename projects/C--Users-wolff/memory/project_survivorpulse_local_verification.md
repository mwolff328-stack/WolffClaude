**The full vitest suite is UNRUNNABLE locally** — it OOMs with `ERR_WORKER_OUT_OF_MEMORY` over the ~4,630-test run (deterministic, identical with `--pool=forks` and `--pool=threads`; a single worker exhausts the JS heap and crashes, cascading ~111 *false-positive* failures). Even a single large directory (`tests/`) OOMs in one process. Do NOT trust a full-suite "X failed" number — it's almost always the OOM cascade, not real failures.

**`/pre-deploy` (`npm run test:prepublish`) confirmed unrunnable locally, 2026-07-18:** the unit step (now 495 files / 7,568 tests, ~3,600s env time) still hits `FATAL ERROR: JavaScript heap out of memory` → one worker fork crashes → vitest reports `Errors 1 error` (0 assertion failures) → the gate's Unit suite exits non-zero and HALTS before Integration/E2E/Regression ever run. `NODE_OPTIONS=--max-old-space-size=8192` does NOT clear it (exhaustion is per-fork, not main-heap). Distinguish real failures from the OOM by re-running the specific files in isolation with `--no-file-parallelism` + a 6GB heap — real failures reproduce there; the OOM does not. This gate MUST be run in CI (adequate memory); locally you can only prove individual files green. **Verify this way instead:**
- `npm run check` (tsc) runs fine and is a reliable gate. **`npm run build` CAVEAT (seen 2026-07-06 via the Bash/git-bash tool):** the Vite client-build step can fail with `'.' is not recognized as an internal or external command` from `execSync('./node_modules/.bin/vite build')` — a shell/path issue, NOT a code error (reproduces on the unmodified tree via `git stash`). The import-guardrail checks that run *before* Vite still pass. Workaround: `NODE_OPTIONS=--max-old-space-size=6144 npx vite build` directly, or run the build in PowerShell instead of the Bash tool. Don't treat this specific failure as a regression; confirm via `git stash` on a clean tree.
- Run **targeted batches** of the changed code's blast radius: `NODE_OPTIONS=--max-old-space-size=6144 NODE_ENV=test TEST_DISABLE_NETWORK=1 TEST_FAST_OPTIMIZER=1 npx vitest run <files> --no-file-parallelism`. Find the blast radius with `grep -rl <changed-symbol> tests/ client/ --include="*.test.ts*"`.
- To decide if a failing test is a **regression vs pre-existing**, git-bisect it: revert your changed source files to the base commit and re-run the test (or `git checkout <base> -- <files>`); if it still fails, it's pre-existing. Confirmed pre-existing-on-base failures as of 2026-06-26: `entryRosterSidebarBuyback.test.tsx`, `pickHistoryTable.test.tsx` (others were fixed).
- `*.integration.test.ts` need the Neon dev DB via `.env` (absent locally) and are excluded from the default unit run — they run in CI only. They at least compile under `npm run check`.

**CI / deploy reality:** pushing to `2026-v1` only triggers the **Replit Sync** workflow (deploys to Replit dev, ~15-25s). The heavy gates — **Pre-Publish Gate**, **Release Guardian**, **Playwright** — do NOT auto-run on branch push; they are the manual/founder-run pre-publish step (the real full-suite + E2E gate). So local targeted batches + CI Pre-Publish Gate together are the verification story; neither alone is complete.

**Test pattern:** prefer booting the real app (`registerRoutes(app)` + supertest) over re-implementing handler copies in tests — mirrored handlers pass while the real route regresses. Template: `tests/authHardening.integration.test.ts`. See [[feedback-survivorpulse-smoke-over-mocks]].
