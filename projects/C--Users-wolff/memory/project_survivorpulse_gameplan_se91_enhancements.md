### Hard-won findings from the SST-958 review (all verified with line numbers)
1. **`storage.createEntry` had exactly ONE caller before SST-958, and it was pool-owner-gated.** Any new non-owner entry-creation route is therefore the FIRST unbounded write path into another user's pool. There is no `/api` rate limiter (the comment at routes.ts:13706 claiming one exists is FALSE), no pagination on `GET /api/pools/:poolId/entries`, and `totalEntries` is a live COUNT — so unbounded creation corrupts another user's pool view.
2. **`pools.maxEntriesPerUser` defaulted to 1 and was NEVER enforced server-side.** It IS enforced client-side (pool-form.tsx:981-984, real user-facing error) and described in a tooltip (:266) — product presented it as a rule the server ignored. Same for `maxEntries`; `entryDeadline` (schema.ts:464) is referenced exactly ONCE in the whole repo (its own definition) — fully dead. ⚠️ **FOUNDER RULING 2026-07-22: default raised 1 → 100** (`e929be26`, schema.ts + pool-form.tsx create default :212 and edit prefill :368). Reason: SST-958 made the column enforced for the first time, so a default of 1 would refuse "+ Add Entry" (SST-960) in almost every existing pool. Founder confirmed NO pool was deliberately set to 1 and authorized a backfill of the 1s. **A schema default change affects NEW rows only — existing rows need a separate UPDATE, and the live DB column default needs an ALTER.** Both must be run in the REPLIT CONSOLE against helium; anything run locally hits ep-flat-rice, a different DB (see [[project_survivorpulse_schema_drift_helium]]). Prod is a third DB, publish-time only.
3. **THE LOCKOUT TRAP (needs founder ruling, filed):** `canParticipateInPool` (routes.ts:250-265) is satisfied ONLY by ADMIN, `pool.createdBy`, or owning ≥1 entry row. The last-entry guard is POOL-WIDE (`storage.getEntries(poolId)` = ALL users, refuse at `<=1`), so in a 50-person pool a user CAN delete their only entry → `canParticipateInPool` false forever → cannot re-add. `/join` writes `pool_participants` (does NOT satisfy the gate), the owner-gated POST hardcodes the CREATOR's userId (commissioner cannot re-add anyone), and Game Plan lists pools BY entries so the pool vanishes. Admin-only undo. Must be ruled BEFORE SST-960 ships the trash icon.
4. **`canParticipateInPool` on PATCH/DELETE can never fail if `canWriteEntry` passed** — non-admin means `entry.userId === user.id`, which is the row it queries for. One wasted DB round trip; reads like defense-in-depth that isn't. Kept for consistency, do not count it as a second gate.
5. **Cascades off `entries`:** only TWO FKs — `picks.entryId` (no onDelete, deleted explicitly in the txn) and `entryFinancialRecords.entryId` (CASCADE). Plus two soft refs with NO FK that go stale: `userPoolEntryOrder.orderedEntryIds` jsonb (schema.ts:827) and `users.defaultEntryId` (:497, comment claims FK but there is no `references()`).
6. **RED-proof technique that beat file-reverting:** wrap each guard in `if (false && ...)` so ALL guards break in ONE run, then assert the exact expected failure count and reason per test. Felix got 6 targeted failures this way. Cheaper and more precise than reverting whole files, and it proves each guard independently.

### Hard-won gotchas from this build
1. **Fixture inconsistency was endemic**: several cockpit test fixtures declared an entry `pickedWeeks:[W]` while the picks mock had NO row for W. Those tests were passing on the archetype SUGGESTION + a badge flag, never a real persisted pick — names like "has a persisted pick" were false. Fixing one fixture cleared 9 failures.
2. **The divergent-state defect (code review catch)**: `picksForEntryWeek` returns `[]` whenever `picksQuery.data` is undefined, and the sections mount as soon as the ENTRIES query resolves — so the picks query is ALWAYS in flight on first paint. Deciding "no pick" from the picks query alone made genuinely-picked weeks flash (and, on fetch failure, permanently show) "No pick yet", with Week View rendering the green Picked chip directly above it, and a tap would silently overwrite the invisible pick (picker PUT is idempotent, no 409). Fix: only treat an odds week as blank when `entry.pickedWeeks` does NOT contain it.
3. `tsconfig` excludes `**/*.test.ts` but NOT `.test.tsx` — so `.test.ts` files typecheck-clean and only fail at runtime. Don't trust tsc to catch fixture drift in `.test.ts`.
4. `CockpitPoolEntriesGroup.poolScheduleType` is a plain `string`, not the union — generic constraints must be `string | null` or inference silently fails.
