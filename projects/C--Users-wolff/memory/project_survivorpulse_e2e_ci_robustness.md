Three Playwright E2E tests failed on 2026-v1 (CI run 28924091047 shard 3), independent of Portfolio ROI work. All were **stale test assertions, not feature regressions**. Fixed in commit 34d648a3 on 2026-v1 (2026-07-08). Pattern mirrors the [[project_survivorpulse_portfolio_roi]] empty-DB robustness treatment in 68b139d8.

**SST-646 pick-grid TC-01/TC-25** (`e2e/pick-grid-status-and-results.spec.ts`): SUPERSEDED by SST-762 (commit `eac8bb05`, 2026-07-08). The 2026-07-06 drawer-for-single-pick routing is GONE — the standalone `RankedTeamDrawer` is DELETED. Every clickable cell (single + multi pick) now opens ONE unified `TeamPickerModal` with a Ranked view (default) + a By Division tab. Ranked-row selection testid is now `ranked-team-toggle-<teamId>` (NOT the old drawer `use-this-<id>`). `team-picker-option-*` and `team-picker-clear` (By Division view) were preserved. `e2e/pick-grid-status-and-results.spec.ts` still uses `use-this-<teamId>` and WILL FAIL until its testids are updated to `ranked-team-toggle-<teamId>`; `e2e/pick-grid-multi-pick.spec.ts` is unaffected. The Ranked view still fetches `GET /api/optimizer/entry-recommendations` (via `queryKeys.entries.optimizerRecommendations(entryId, scheduleType, season, week)`), so a MOCK entry id needs that endpoint mocked or it 500s.

**SST-456 pool-rules-upload** (`e2e/pool-rules-upload.spec.ts:454`): `goto('/pools')` + `waitForLoadState('networkidle')` never settles on CI (pools page keeps background queries in flight) + `getByRole('link',{name:/settings/i})` link-hunt could match global nav. Fix: navigate straight to `/pools/${picksPoolId}/settings` and wait on `settings-section-basics` — the deterministic pattern `pool-settings-redesign.spec.ts` already uses (`readFixtures().picksPoolId`, DATA_TIMEOUT=20s, test.setTimeout 60s). Settings Basics section renders `<Step1Basics>` which owns `rules-upload-box`.

**Rule of thumb:** in the ephemeral CI harness, never `waitForLoadState('networkidle')` (use a concrete testid). Post-SST-762: ALL cells open the unified `TeamPickerModal` (Ranked default, `ranked-team-toggle-<id>`; By Division `team-picker-option-*`) — there is no drawer anymore. Dispatch a focused re-run: `gh workflow run playwright-ci.yml --ref 2026-v1 -f test_spec="<specs>" -f shards=1`.

**2026-07-11 follow-up (run 29106013575 → fixed in commit 93e5d4be, re-run 29157758918 all 6 shards GREEN).** Two more independent failures, both FIXED:
1. **SST-762 hidden-tab stale spec** (`e2e/pick-grid-multi-pick.spec.ts` TC-10/TC-16 :283, TC-20 :351): the a36ab80a audit claimed multi-pick unaffected because `team-picker-option-*` testids still EXIST — but they now live in the By Division panel which is `hidden` while the modal defaults to Ranked. Symptom: `locator resolved to <button…> … 221× waiting for element to be visible` → click timeout. Lesson: testid-still-exists ≠ testid-still-visible; the unified modal opens on Ranked, so any By Division interaction MUST first click `[data-testid="team-picker-tab-division"]`. Fix added `openDivisionTab()` + mocked `/api/optimizer/entry-recommendations` → `{allTeams:[]}` (Ranked view fires it on open; synthetic entry 500s otherwise, exactly as this file predicted). TC-18 :324 was unaffected (its `team-picker-clear` is in the always-visible header).
2. **Cross-shard fixtures DB race** (`e2e/fixtures.setup.ts` provision): all 6 shards SHARE one Neon test DB and each runs the `fixtures` setup project; they race to POST the same `(entry, period, team)` fixture pick → loser 500s on `unique_entry_period_team` → because `chromium` project `dependencies: ['setup','fixtures']`, a fixtures failure cascades to "**72 did not run**" on that shard (shard 2). This is why one shard shows a fixtures 500 + everything skipped, while another shard shows the real spec failures — DIFFERENT root causes per shard in the same run. Fix: made provisioning idempotent/race-tolerant (`entryHasFixturePick()` GET `/api/pools/:poolId/entries/:entryId/picks` — skip POST if pick exists; on racing 500 re-verify DB state before failing), NOT a product-endpoint change (the unique constraint is a legit invariant). When shards 2+3 both "fail", pull EACH shard's log separately — they can fail for unrelated reasons.

**2026-07-14 (SST-784 new spec `e2e/historical-pool-data.spec.ts`, run 29350761318 → fixed b2cf16d3 → green 29351124962).** The seeded fixture pool `E2E Fixture Pool - picks` is provisioned TWICE on CI — once by `scripts/seed-e2e.ts` (setup job) and once by `e2e/fixtures.setup.ts` — so a pool-select dropdown shows TWO identically-named `E2E Fixture Pool - picks (2025)` options. `getByRole('option', {name:/E2E Fixture Pool - picks/})` then hits a Playwright **strict-mode violation (resolved to 2 elements)** and fails `toBeVisible`/`click`. Fix = append `.first()` (both duplicates are the same fixture data, same 2025 season). This is already the suite-wide convention: `pool-creation-wizard`, `pool-payout-structure`, `pool-rules-upload`, `pool-pick-rules-multipick`, `picks-slot-coverage` all do `option.first()`. ANY new spec selecting the fixture pool from a dropdown MUST use `.first()`. Also: `-f test_spec="<one spec>"` still fans across all 6 shards (empty shards pass trivially); pull only the failing shards' logs. Typecheck of `e2e/**` needs a scratch tsconfig — the spec dir isn't in the main `tsconfig.json` include, so `npm run check` alone won't catch spec type errors. Broader recurring lesson (2nd time this session, cf. Deb's scheduleType bug): typecheck+unit green ≠ verified; the ephemeral harness is the real gate.
